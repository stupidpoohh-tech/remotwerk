# Remotwerk

두 사람(연인)이 함께 쓰는 **데스크톱 캐릭터 앱**. 각자 자신의 캐릭터를 고르면,
내 캐릭터가 상대의 화면 위에 상주하며 살아 움직이고, 상대의 캐릭터가 내 화면 위에
상주한다. 나는 리모컨으로 간단한 동작을 발사하고, 그 동작은 상대 화면에 있는
내 캐릭터가 수행한다.

메신저가 아니다. 텍스트가 아니라 **몸짓으로, 답장을 요구하지 않는 낮은 대역폭의
신호**를 주고받는 현존(presence) 아바타다. 업무 중 곁눈질 한 번에 읽히는 작고
귀여운 신호가 핵심 경험이다.

## 핵심 설계 원칙 (위반 금지)

1. **비침습성** — 오버레이는 작업 영역을 가리지 않고, 캐릭터 밖 영역은 클릭을 통과시킨다.
2. **무압박** — 읽음/응답 표시를 만들지 않는다. 신호는 도착까지만, 봤는지는 알리지 않는다.
3. **곁눈질 가독성** — 신호 하나가 하나의 또렷한 동작으로 즉시 읽힌다.
4. **상대 상태 비감시** — 화면 속 캐릭터의 자율 생활은 상대의 접속·활동을 반영하지 않는다.

## 실행

```bash
npm install
npm start
```

- Electron(Windows·macOS)에서 동작. 투명·항상 위·클릭 통과 동작은 OS별 세부가
  다르므로 각 플랫폼에서 확인이 필요하다.
- 최초 실행 시 **설정 창**이 뜬다. Firebase 설정을 비워 두면 **로컬 데모 모드**로
  실행되어, 같은 PC 안에서 리모컨→오버레이 흐름을 끝에서 끝까지 확인할 수 있다.

### 조작

| 기능 | 방법 |
|------|------|
| 리모컨 열기 | 캐릭터를 **톡 클릭**, 트레이 아이콘 좌클릭, 또는 트레이 메뉴 |
| 설정 열기 | 실행하면 자동으로 뜬다. `Ctrl/Cmd + Shift + S` 또는 트레이 메뉴·작업표시줄 |
| 즉시 숨김/복원 (보스키) | `Ctrl/Cmd + Shift + H` |
| 집중 모드 · 자동 시작 | 트레이 메뉴 체크 |
| 히스토리 · 캐릭터 만들기 · 동작 뷰어(디버그) | 트레이 메뉴 |
| **캐릭터를 잃어버렸을 때** | 트레이 메뉴 → **캐릭터 화면 가운데로 되돌리기** |
| 캐릭터 이동 | 캐릭터를 드래그 (모니터 경계를 넘어 이동 가능) |
| 캐릭터 크기 | 캐릭터에 마우스를 올리면 나타나는 **모서리 핸들** 드래그, **휠 스크롤**, 우클릭 → 크기, 설정창 슬라이더 |
| 리모컨 열기(빠른 길) | 캐릭터를 **톡 클릭**, 또는 트레이 아이콘 좌클릭 |
| 종료 · 숨기기 | 캐릭터 **우클릭** → 메뉴 |

## 빌드 · 배포

```bash
npm install
npm test             # 렌더러 공유 모듈 회귀 테스트(tools/selftest.js, 의존성 없음)
npm run dist:win     # → dist/Remotwerk-Setup-<버전>.exe (NSIS 설치파일)
npm run pack         # 설치파일 없이 폴더로만 빌드(빠른 확인용)
```

- **회귀 테스트**: `npm test` 는 DOM 없이 돌아간다. 제스처↔애니메이션 대응, 애니메이션
  데이터의 오타(엔진이 조용히 무시하는 잘못된 키), 트랙 보간(계단/선형), 5조각 골격 비율,
  번들→리그 변환, 자르기 fit 역회전 왕복, 미리보기 배치(발·머리 잘림), 각 화면의 CSP,
  그리고 스프라이트 클립 규격(캔버스·기준점·접지·접합 자세·리그 대체)을 검사한다.

```bash
node tools/app-smoke.js   # ★ 진짜 앱을 띄워 캐릭터가 실제로 보이는지 확인(설정 25가지)
node tools/flag-check.js  # 업로드 진입점이 실제로 막혔는지 + 기존 캐릭터 보존
node tools/overlay-startup-test.js  # 네트워크가 끝나지 않을 때도 캐릭터가 뜨는지(npm test 에 포함)
node tools/anim-check/render.js && python3 tools/anim-check/check.py  # 프레임 단위 검사
node tools/anim-check/timeline.js        # 실제 재생 시간축 검사(스프라이트)
node tools/anim-check/timeline.js --rig  # 〃 (리그 호환 경로)
python3 tools/build-clip-art.py          # 클립 규격 검사 + 등록부 재생성
```

> **렌더러만 열어 보고 "된다"고 판단하지 않는다.** 렌더러 검사는 통과하는데 실제 앱에서는
> 캐릭터가 안 보이는 일이 있었다(설정값 때문에 화면 밖으로 나가거나, 빈 캐릭터라 아무것도
> 안 그려지거나). `tools/app-smoke.js` 는 Xvfb 위에서 **진짜 Electron 앱**을 띄우고,
> 사용자가 실제로 만들 수 있는 설정 상태 11가지에서 캐릭터가 화면에 보이는지 확인한다.
>
> **정지 이미지 한 장으로 애니메이션을 판단하지 않는다.** 리그·클립·아트를 건드리면
> 위 도구로 **재생 중인 화면을 시간축으로** 확인한다.

- **패키징**: `electron-builder`. Windows 는 NSIS 설치파일(사용자 단위 설치라 관리자 권한
  불필요), macOS 는 dmg, Linux 는 AppImage.
- **아이콘**: `build/icon.png`(1080×1080) 하나로 각 플랫폼 아이콘이 자동 생성된다.
  실제 아트가 들어와 있으므로 `npm run icon`(플레이스홀더 생성기)은 **기본적으로 아무 일도
  하지 않는다**(`--force` 로만 덮어쓴다). 빌드 워크플로에서도 이 단계를 뺐다 —
  CI 가 실제 아이콘을 플레이스홀더로 되돌리는 사고를 막기 위해서다.
- **자동 시작**: 설정창 또는 트레이에서 켤 수 있다(`app.setLoginItemSettings`).
  자동 시작으로 켜진 실행은 설정창을 띄우지 않고 조용히 시작한다.
- **자동 업데이트**: `electron-updater` + GitHub Releases. **패키징된 빌드에서만** 동작하며
  (`app.isPackaged`), 6시간마다 확인하고 종료 시 적용한다.
  `npm run release` 로 배포하려면 `GH_TOKEN` 환경변수가 필요하고, **비공개 저장소면
  일반 사용자가 업데이트를 받을 수 없으므로** 릴리스는 공개 저장소여야 한다.
- **작업표시줄**: 설정 창이 **대표 창**이다. 오버레이는 투명·클릭 통과·포커스 없음이라
  작업표시줄에 뜰 수 없다(뜨게 만들면 캐릭터를 누를 때마다 작업 중인 창에서 포커스를
  빼앗아 비침습성 원칙을 어긴다). 그래서 평범한 창인 설정 창을 대표로 두고,
  실행하면 자동으로 띄우며 닫기를 누르면 **최소화**한다 — 앱이 켜져 있는 동안
  작업표시줄에서 계속 보인다. 완전히 끄는 것은 트레이·캐릭터 우클릭의 '종료'.
- **트레이 아이콘**: `src/main/tray-16.png`·`tray-32.png`(실제 앱 아이콘). 정체불명의
  도형이면 사용자가 앱을 못 찾는다(Windows 11 은 새 트레이 아이콘을 숨김 영역에 넣는다).
- **로그**: 처리되지 않은 예외와 **오버레이 시작 상태**(창 좌표·모니터 수·캐릭터 위치·
  선택된 캐릭터)를 `userData/logs/main.log` 에 남긴다(1MB 넘으면 새로 시작).
  설정창의 "로그 폴더 열기"로 바로 열 수 있다.

> ⚠️ **코드 서명은 아직 설정하지 않았다.** 서명 없는 설치파일은 Windows SmartScreen 이
> "알 수 없는 게시자" 경고를 띄운다(*추가 정보 → 실행*으로 진행 가능). 공개 배포 시에는
> 코드 서명 인증서 도입을 검토해야 한다.

## 제품 방향 — 제공형 캐릭터

사용자가 이미지를 올려 캐릭터를 만드는 기능은 **기본 꺼짐**이다(`src/features.js` 의
`characterUpload`). 우리가 제작·검수한 캐릭터를 고르는 서비스로 운영한다.
업로드 구현(리깅 도구)은 **지우지 않았다.** 플래그만 켜면 그대로 돌아온다.

- 플래그 하나(`src/features.js`)를 **메인·preload·설정 화면이 같이 본다.** preload 가
  `window.rwHost.features` 로 그대로 넘긴다. 값을 두 군데 적으면 반드시 어긋난다.
- 화면에서 버튼만 숨기는 것은 끈 게 아니다. `createRigger()` 와 `ui:open-rigger` IPC
  핸들러도 같은 플래그로 막는다. IPC 로 강제로 열어도 창이 뜨지 않는 것을
  `tools/flag-check.js` 가 진짜 앱에서 확인한다.
- **기존 개인 캐릭터는 그대로 둔다.** 목록에 보이고, 고를 수 있고, 상대에게 전달되고,
  재시작해도 남는다. 없어지는 것은 "만들기"·"편집" 버튼뿐이다(삭제는 남긴다 — 이미
  가진 것을 정리하는 일은 새로 만드는 기능이 아니다).

### 원화 반입

원화는 바깥 제작 환경에서 만들고, 여기서는 **정규화·가져오기·검사·연결**만 한다.
절차 전체는 `docs/art-orders.md` 의 "넣는 방법", 규격은 `art/staging/README.md`.

```bash
python3 tools/normalize-art.py <캐릭터> twerk_loop \
    --match art/clips/<캐릭터>/idle/frame-00.png <원화 4장>   # 배율·접지·좌우 기준 정렬
python3 tools/import-clip.py  <캐릭터> twerk_loop --write     # 규격 검사 후에만 반영
python3 tools/turn-frames.py  <캐릭터>                        # 뒤돌기 이음매를 춤 첫 장에 맞춤
python3 tools/build-clip-art.py
```

- 규격을 못 넘기면 **아무 파일도 쓰지 않는다**(기존 정상 에셋 보호).
- `--approve` 없이는 `placeholder` 가 유지된다. 파일이 있다는 이유로 풀지 않는다.
- 가져온 클립(`source: "import"`)은 `tools/bake-placeholder-clips.js` 가 **건너뛴다**
  (`--force` 로만 덮어씀). 이게 없을 때 실제로 원화가 임시본으로 되돌아갔다.
- **접지 판정 임계값은 세 도구가 알파>0 으로 같다.** 서로 다르면 앞 단계를 통과한
  그림이 다음 단계에서 "발바닥이 몇 px 어긋난다" 로 걸린다.

## 동작(신호) 목록

**능동 4개 (리모컨)** — 움직임 방향과 이펙트 색으로 이중 구분한다.

| 신호 | 의미 | 움직임 | 이펙트 |
|---|---|---|---|
| 💗 **보고싶어** | 애정 | **위로** 작게 두 번 폴짝 + 몸 살랑 | 분홍 하트 ↑ |
| ✨ **신나** | 기쁨·응원 | **크게 세 번 연속 점프** | 노랑 반짝 |
| 🫠 **지쳤어** | 힘듦·투정 | **아래로** 푹 눌려 좌우로 흔들 | 파랑 땀방울 ↓ |
| 🍑 **트월킹** | 장난·애교 | **뒤로 돌아** 엉덩이를 좌우로 둠칫둠칫 | 없음(등을 보이는 것 자체가 신호) |

방향(위/반복/아래/뒤) · 속도 · 색이 모두 달라 곁눈질로 갈린다.

> 트월킹은 앱 이름값을 하는 시그니처 동작이다. 리깅 도구에서 **뒷모습 이미지**를 함께
> 등록하면 실제로 등을 보이고, 없으면 몸을 얇게 눌러 도는 인상만 준 뒤 앞모습으로
> 흔든다(등록하지 않아도 깨지지 않는다).

> 8개였던 것을 3개로 줄였다(트월킹을 더해 지금은 4개다). 아이콘만으로 외워지지 않았고, 5조각 치비 리그로는 8가지를
> 시각적으로 구분할 수 없었다(뒹굴기/좌절은 둘 다 아래로, 부비기/으쓱은 둘 다 제자리 상체).
> 자리비우기(사라짐)도 뺐다 — 캐릭터가 없어지면 상대는 신호가 아니라 오작동으로 읽었다.

**자율 생활 2종 (신호 아님, 로컬 반복)** — 😐 멍때리기 · 🚶 돌아다니기.
전송되지 않고 히스토리에도 남지 않으며, 상대의 접속 여부와 무관하다.

## 구조

```
src/
  main/
    main.js         # 창 관리(오버레이·리모컨·히스토리·설정), 단축키(보스키·설정), 트레이
    preload.js      # 렌더러↔메인 브리지(설정/창 제어/클릭 통과)
    config.js       # userData/config.json 저장소(페어링·캐릭터·집중 모드)
  renderer/
    overlay/        # 상대 캐릭터 상주 + 신호 라이브 재생 + 자율 생활 + 드래그
    remote/         # 리모컨 — 내 캐릭터 미리보기 + 신호 4버튼
    history/        # 오늘 받은 신호 목록
    settings/       # 페어링 코드/캐릭터 선택((+) 리깅 도구)/Firebase 설정
    rigger/         # 리깅·업로드 도구(大자 5조각 정합 → 커스텀 캐릭터) — Prompt B
    viewer/         # 동작 뷰어(디버그) — 캐릭터 골라 동작 즉시 재생
    shared/
      skeleton.js   # 이족 골격(상세 bipedal + 5조각 bipedal5)
      gestures.js   # 신호 메타데이터(id·이름·아이콘) — 능동 4 + 자율 2
      animations.js # 골격별 키프레임 시퀀스(신호 4 + 자율 2)
      engine.js     # 골격 기반 재생 엔진(트랙 보간·이징·블렌딩, animSource 리매핑, fit 렌더)
      clip-art.js   # 스프라이트 클립 등록부(경로·유지시간·접지·bbox) — 자동 생성
      clips.js      # 클립 조회 + 신호→클립 조합 계획(g_twerk = 뒤돌기→트월킹×3→앞돌기)
      player.js     # 재생기 — 스프라이트와 리그를 같은 인터페이스로 감싼다
      actor.js      # 상태 제어(대기·걷기·신호) + 화면 이동(좌표·속도·걸음 보폭)
      presets.js    # 제공 캐릭터 로더(그림 프리셋)
      preset-art.js # 제공 캐릭터 5조각 아트(data URI) — 자동 생성
      characters.js # 프리셋+공용 카탈로그+개인 통합 해석기(번들→리그)
```

## 애니메이션 구조 — 세 층으로 나눠져 있다

한 덩어리였던 재생 코드를 역할로 갈랐다. 각 층은 아래 층이 무엇인지 몰라도 된다.

| 층 | 파일 | 하는 일 | 하지 않는 일 |
|---|---|---|---|
| **상태 제어** | `actor.js` | 대기·걷기·신호 사이의 전환, 신호 대기열(최대 1개), 끼어들기 규칙 | 그림을 고르지 않는다 |
| **클립 재생** | `player.js` | 클립 한 개를 경과 시간으로 재생, 프레임별 유지 시간, 루프 구간, 종료 통보 | 캐릭터를 화면에서 옮기지 않는다 |
| **화면 이동** | `actor.js` 의 이동부 | 화면 좌표·속도·방향, 걸음 보폭↔이동 거리 | 자세를 만들지 않는다 |

- **재생기는 두 가지 구현을 같은 인터페이스로 감싼다.** 캐릭터에 필요한 클립이
  **전부** 있으면 스프라이트로, 하나라도 없으면 **기존 5조각 리그**로 재생한다
  (`RW.player.canUseSprite`). 업로드한 커스텀 캐릭터는 클립이 없으므로 항상 리그다.
  즉 **기존 캐릭터는 아무것도 깨지지 않는다.**
- **클립 안의 자세와 화면 좌표는 완전히 분리한다.** 걷기 클립은 제자리걸음으로
  만들고(`stepAdvance` 로 한 걸음이 몇 픽셀인지만 적는다), 실제 이동은 상태 제어가
  좌표에 더한다. 이렇게 하지 않으면 이동이 두 번 적용돼 발이 미끄러진다.
- 오버레이·리모컨·설정·뷰어가 **모두 같은 재생 경로**를 쓴다. 한 곳에서만 자연스럽고
  다른 곳에서 어색해지는 일이 없다.
- 제작 기준(캔버스·기준점·접합 자세·프레임 예산·승인 기준)은 `docs/animation-bible.md`.

> ⚠️ **현재 물개(`char_seal`)의 클립 42장은 임시 에셋이다.** 새로 그린 그림이 아니라
> 원본 5조각을 엔진으로 자세만 잡아 구운 것이다(`clip.json` 의 `placeholder: true`).
> 재생 구조·타이밍·접지를 실물로 검증하기 위한 것이며 **최종 아트 품질이 아니다.**
> 진짜 그림은 `docs/art-orders.md` 대로 그려 같은 경로에 넣으면 코드 수정 없이 교체된다.

## 골격 애니메이션 엔진(리그 경로)

- 골격은 **이족(bipedal)** 으로 고정. 각 골격은 고정된 관절 슬롯(머리·몸통·좌우
  팔·좌우 다리)을 가진다.
- 애니메이션은 캐릭터가 아니라 **골격**에 대해 만든 키프레임 시퀀스다. 같은 골격이면
  어떤 캐릭터를 올려도 같은 시퀀스가 그대로 적용된다.
- 엔진은 희소 키프레임을 **본별 트랙**으로 펼쳐 선형 보간한다(회전·이동·스쿼시).
  가시성/좌우반전은 계단 보간한다.
- 치비 체형에서는 관절을 꺾어도 잘 안 읽히므로, 표현의 무게중심을 **몸 전체의 이동·
  스쿼시(sx/sy)** 에 둔다. 변형 기준점은 발밑이라 "바닥에 선 몸"으로 읽힌다.
- **이펙트 레이어**(하트·반짝·땀방울)는 골격과 무관해 신호를 구분짓는 가장 확실한
  수단이다. 종류는 애니메이션 메타가 정하고 세기는 트랙이 보간한다.
- 키프레임마다 **이징**(`linear`/`in`/`out`/`inOut`/`back`)을 줄 수 있다. 기본은 `inOut`.
- **루프 클립은 끝 자세를 시작 자세로 자동으로 닫고**(`closeLoop`), 1회성 신호는
  `settle` 로 대기 자세까지 마무리 키프레임을 덧붙인다. 이전에는 신호가 끝나는 순간
  팔이 20~24° 남은 채 다음 대기 동작으로 홱 튀었다.
- 신호를 시작할 때는 **지금 자세에서 블렌딩**해 들어간다(기본 180ms). 걷는 중에
  신호가 와도 첫 프레임으로 순간이동하지 않는다.

## 렌더러 CSP — 여기 빠지면 앱이 조용히 멈춘다

각 화면의 `<meta http-equiv="Content-Security-Policy">` 에 Firebase 가 실제로 쓰는 주소가
전부 들어 있어야 한다.

**통로마다 걸리는 지시어가 다르고, 그게 직관과 어긋난다.**

| 용도 | 주소 | 어느 지시어에 걸리는가 |
|---|---|---|
| Firebase SDK 동적 import | `https://www.gstatic.com` | `script-src` |
| DB REST | `https://*.firebasedatabase.app` | `connect-src` |
| **DB 롱폴링** | **`https://*.firebasedatabase.app`** | **`script-src`** ← fetch 가 아니라 `<script>` 주입이다 |
| DB 실시간 | `wss://*.firebasedatabase.app` | `connect-src` |
| 익명 인증 · Storage | `https://*.googleapis.com` | `connect-src` |

> 구형(미국) 인스턴스를 쓰면 위의 `firebasedatabase.app` 자리가 `firebaseio.com` 이 된다.
> 둘 다 넣어 둔다.
>
> **롱폴링이 `script-src` 를 받는다는 것이 함정이다.** RTDB 는 WebSocket 이 막힌 망에서
> 롱폴링으로 넘어가는데, 이 통로가 `<script src="…/.lp?…">` 주입이라 `connect-src` 로는
> 열리지 않는다. 여기가 빠져 있으면 **WebSocket 도 롱폴링도 막힌 채**, 화면에는
> "네트워크를 확인하세요" 라고만 나온다 — 실제로 사용자에게 망 탓이라고 잘못 안내했다.

```bash
node tools/csp-check.js   # 6개 화면 × 5가지 통로를 진짜 브라우저에서 확인
```

CSP 위반은 네트워크 없이도 발생하므로 이 검사는 오프라인에서도 정확하다.
그리고 연결 진단은 연결을 시도하는 동안 `securitypolicyviolation` 을 함께 들어서,
**앱이 스스로 막은 것**과 바깥 망이 막은 것을 구분해 보고한다.

> v0.6.x 에서 초대 코드 만들기가 "방을 만드는 중…" 에서 멈춘 원인이 마지막 줄이었다.
> 이 DB 는 싱가포르 지역 인스턴스라 실시간 연결이 `wss://*.firebasedatabase.app` 인데
> CSP 에는 `wss://*.firebaseio.com` 만 있었다. **RTDB 의 쓰기는 서버가 응답할 때까지
> 끝나지 않으므로**, 연결이 막히면 오류도 없이 영영 대기한다 — 화면에는 그냥 멈춘 것처럼
> 보인다. `npm test` 가 이제 모든 화면의 CSP 를 검사한다.
>
> 같은 이유로 페어링은 쓰기 전에 `.info/connected` 로 연결을 먼저 확인하고, 각 단계에
> 15초 상한을 둔다. 설정창에는 서버 연결 상태를 항상 표시한다.

## 연결 진단 — 증상이 같고 원인이 다른 네 가지

"서버에 연결되지 않았어요" 는 **원인을 말해 주지 않는다.** 아래 넷은 화면상 증상이 똑같은데
해야 할 일이 전혀 다르다. 그래서 설정창에 **연결 진단** 버튼을 두고 단계별로 갈라낸다.

| 어디서 막히는가 | 어떻게 알아내는가 | 해야 할 일 |
|---|---|---|
| SDK·익명 로그인 | `fb.init()` 이 던지는 오류 | 콘솔 → Authentication → 익명 켜기 |
| 그 주소에 DB 가 없다 | REST `GET <databaseURL>/.json` 이 404 또는 무응답 | 콘솔 → Realtime Database 만들기 |
| 주소가 다른 리전이다 | 리전별 기본 주소를 차례로 찔러 살아 있는 것을 찾는다 | **앱이 버튼 한 번으로 고친다** |
| 소켓(wss)만 막혔다 | REST 는 되는데 `.info/connected` 만 안 된다 | 회사망·VPN·방화벽 |

핵심은 **REST 로 먼저 찔러 보는 것**이다. REST 는 평범한 https 요청이라, 이게 되면
주소는 맞다는 뜻이고 남은 문제는 소켓뿐이다. `401 Permission denied` 도 **연결됐다는 증거**로
읽는다(규칙이 막았을 뿐 DB 는 있다).

```bash
node tools/diag-check.js   # 5가지 상황을 실제 설정 화면에서 재현해 문구까지 확인
```

## 보안 모델 · Firebase 데이터 모델

**접근 권한은 "코드를 아는가"가 아니라 "이 uid 가 그 방의 멤버인가"로 판단한다.**

- **익명 인증**(`signInAnonymously`)으로 설치마다 서버가 발급·검증하는 uid 를 받는다.
- **방 id 는 서버가 만든 추측 불가능한 push key.** 초대 코드는 `invites/{code} → roomId`
  매핑일 뿐이며 **1회용 + 24시간 만료**다. 참여 즉시 삭제되고, 이후엔 코드가 없어도 이어진다.
- **방 정원은 좌석 2개(`a`·`b`)로 고정.** 각 좌석은 비어 있을 때 본인 uid 로만 한 번
  쓸 수 있어서 세 번째 사람은 앉을 자리가 없다.
  (RTDB 보안 규칙에는 자식 개수를 세는 `numChildren()` 이 없으므로 좌석 방식으로 구현했다.)
- 초대 코드는 혼동 문자(I·O·0·1)를 뺀 32글자 × 10자리 = **약 1.1×10¹⁵ 조합**이라
  전수 조사가 불가능하다.

> 이전 모델은 `rooms/{코드}` 를 코드만 알면 누구나 읽고 쓸 수 있었고, 코드가
> `BEAR-5607` 형태로 약 7만 가지뿐이라 **전수 조사로 남의 방에 침입할 수 있었다.**
> 공개 배포를 위해 위 구조로 교체했다.

```
invites/{code}:            { roomId, createdBy, expiresAt }   # 1회용·24h·참여 후 삭제
rooms/{roomId}/
  a: <uid>                 # 좌석 1 (방을 만든 쪽) — 비어 있을 때 본인 uid 로만 1회 쓰기
  b: <uid>                 # 좌석 2 (참여한 쪽)   — 〃, a 와 달라야 함
  members/{uid}:           { characterId, characterRef, joinedAt, lastSeen }
  signals/{pushId}:        { from, gestureId, ts }
```

Storage(커스텀 캐릭터 번들):

```
rooms/{roomId}/characters/{uid}/bundle.json   # 쓰기는 본인 uid 폴더만
```

- 신호 하나는 `{ from, gestureId, ts }` 로 매우 가볍다.
- **온라인**: 상대 클라이언트가 실시간 수신해 내 캐릭터로 라이브 재생 + 히스토리 기록.
- **오프라인**: 신호는 Firebase에 남아 있다가, 상대가 다음에 앱을 켰을 때
  **히스토리에만** 표시(라이브 재생 안 함).
- 판별: 클라이언트는 실행 시작 시각을 기록하고, 수신 `ts` 가 그 이후면 라이브,
  이전이면 히스토리로 처리한다.
- 히스토리는 상대가 보낸(from ≠ 나) **오늘(KST)** 신호만. 로컬 자정(KST)에 비운다.
  하루 이상 지난 신호는 베스트 에포트로 정리한다.

### 프로젝트 설정 (remotwerk-aa0d2)

앱은 기본으로 Firebase 프로젝트 `remotwerk-aa0d2` 에 연결된다(설정은
`src/main/config.js` 의 기본값).

> 웹 API 키는 클라이언트 공개용이라 커밋해도 안전하다(비밀이 아님). 실제 접근 보호는
> **익명 인증 + 보안 규칙**이 담당한다.

콘솔에서 한 번 해둘 것:

1. **익명 인증 켜기** — Authentication → **로그인 방법** → **익명** → 사용 설정.
   **이게 꺼져 있으면 앱이 로그인하지 못해 페어링·신호가 전부 실패한다.**
2. **Realtime Database 생성** — Build → Realtime Database → 인스턴스 생성
   (이 프로젝트는 **싱가포르 `asia-southeast1`**, `config.js` 의 `databaseURL` 이 이미 그 값).
3. **RTDB 보안 규칙** — 저장소 루트 **`database.rules.json`** 을 Realtime Database →
   **규칙** 탭에 붙여넣고 **게시**.

   > **`.indexOn` 이 중요하다.** 히스토리 조회가 `orderByChild('ts')` 를 쓰기 때문에
   > `signals` 에 `.indexOn: ["ts"]` 가 없으면 조회마다 "Using an unspecified index" 경고와
   > 함께 클라이언트에서 전량 필터링해 느려진다.

4. **Storage 보안 규칙** — 저장소 루트 **`storage.rules`** 를 Storage → **규칙** 탭에
   붙여넣고 **게시**. (쓰기는 본인 uid 폴더만, 읽기는 로그인 사용자만)

테스트 모드로 만들었다면 **30일 뒤 전부 차단**되므로 만료 전에 위 규칙으로 교체해야 한다.

> ⚠️ **기존 사용자 재페어링 필요.** 보안 모델을 바꾸면서 경로가 `rooms/{코드}` →
> `rooms/{roomId}` 로 바뀌었다. 예전 `pairCode` 만 있고 `roomId` 가 없는 설치는 자동으로
> 로컬 데모 모드로 떨어지므로, 설정창에서 **초대 코드를 새로 발급/참여**해야 한다.

### Firebase 없이 검증 (로컬 데모)

설정에서 Firebase를 비워 두면 `BroadcastChannel` 기반 **로컬 루프백**으로 동작한다.
리모컨에서 보낸 신호가 '상대'로서 내 오버레이에 되돌아와 재생되고 히스토리에 쌓인다.
아트·안무·상호작용을 실제 Firebase 없이 끝에서 끝까지 확인하기 위한 모드다.

## 제공 캐릭터

앱에 두 캐릭터가 들어 있다. **🦭 물개**와 **🎀 리본**이며, 앞모습·뒷모습 모두 5조각으로
잘라 내장했다(🍑 트월킹에서 등을 보인다).

- 아트는 `preset-art.js` 에 **data URI** 로 들어 있다. 렌더러가 `file://` 로 열리고 CSP 가
  `img-src 'self' data:` 라, 파일 경로 이미지는 창마다 상대경로가 달라지고 CSP 에도 걸릴 수
  있기 때문이다.
- 상대에게는 **캐릭터 id 만** 보낸다. 양쪽 앱에 같은 그림이 들어 있으니 업로드·다운로드가
  아예 없다(개인 제작 캐릭터만 Storage 를 거친다).
- 조각은 회전 없는 사각형으로 잘랐다 → **그림에 그려진 大자 포즈가 곧 기본 자세**이고,
  애니메이션이 어깨·골반 회전으로 그 위에 얹힌다.
- 다시 만들려면 `art/presets/` 의 원본을 고치고 `python3 tools/cut-preset-art.py` 를 돌린다.
  자르기 상자·관절 위치는 그 스크립트 맨 위 `CHARS` 에 좌표로 적혀 있다.

색 도형 프리셋 3종(`preset1~3`)은 아트가 없던 시절의 플레이스홀더인데, 지우면 그걸 고른
사용자의 캐릭터가 사라지므로 목록 뒤에 남겨 두었다.

> **캐릭터 상자와 배치**: 캐릭터마다 몸통·다리 길이가 달라서, 화면 배치를 CSS 고정값으로
> 두면 어떤 캐릭터는 발이, 어떤 캐릭터는 머리가 잘렸다. 이제 `skeleton.contentBox()` 가
> 실제로 그려지는 조각들을 덮는 상자를 계산하고, `engine.fitAnchor()` 가 그 상자로
> 발을 바닥선에 맞춘다. 오버레이의 드래그 히트박스도 같은 상자를 쓴다.

### 5조각 캐릭터가 찢어지지 않게 하는 것들

v0.6.0 은 **움직이면 몸이 잘려 나갔다.** 뉴트럴 포즈만 보고 정상이라 판단한 탓이다.
원인은 하나가 아니라 넷이었고, 넷 다 고쳐야 멀쩡해졌다.

1. **다리를 몸통에 붙였다.** 5조각 리그의 '몸통'은 머리까지 포함한 몸 전체다. 다리가
   골반(root)에 붙어 있으면 몸통이 기울 때 다리만 제자리에 남아 **허리가 찢어진다.**
   `torso` 의 관절이 골반이므로 부모만 바꾸면 좌표는 그대로 쓸 수 있다.
2. **관절 회전을 감쇠한다**(`bone.animScale`). 애니메이션은 팔다리가 가늘고 머리가 따로
   있는 상세 골격 기준으로 만들었다. 치비에 몸통 20°·팔 38° 를 그대로 주면 몸이 반으로
   접히고 팔이 머리 위로 넘어간다. 몸통 0.45 / 팔 0.55 / 다리 0.7 로 줄였다.
   치비의 표현은 원래 관절보다 몸 전체의 이동·스쿼시가 담당한다(설계 원칙과 같은 방향).
3. **조각을 관절 너머까지 물려서 자른다.** 딱 맞게 자르면 조금만 돌아도 이음매가 벌어진다.
   물린 부분은 **관절 중심 원(탭)** 으로 깎는다 — 원은 자기 중심으로 돌아도 같은 원 안에
   머무니까 몸 밖으로 삐져나오지 않는다. 사각형으로 물리면 모서리가 돌아 나와서, 물개
   신나 동작에서 반바지 색 띠가 허리 위로 튀어나왔다.
4. **팔다리를 전부 몸통 뒤(z)에 그린다.** 앞에 두면 물려 둔 부분(몸통 그림 조각)이 몸 위에
   겹쳐 보인다.

검사는 `tools/anim-check/` 로 한다(README 참고). 모든 동작의 모든 프레임을 그려서
분리·구멍·관절 틈을 자동으로 재고, 동작별 시트로 묶어 눈으로도 본다.

## 커스텀 캐릭터 — 리깅·업로드 도구 (Prompt B)

사용자가 직접 이미지를 올려 자신의 캐릭터를 만드는 인앱 도구. 캐릭터 선택 UI의
**(+) 버튼**(설정 창) 또는 트레이 "캐릭터 만들기"로 연다.

- **전체 이미지 1장에서 잘라 쓴다**: 캐릭터 전체 투명 PNG 한 장을 올리면, 그 위에서
  5개 자르기 상자(회전 가능)를 맞춰 조각을 만든다. 부위별로 미리 잘라 둘 필요가 없다.
  잘린 조각의 좌표는 "관절 기준으로 회전시키면 원래 자리"가 되도록 역산하므로,
  **그림에 그려진 포즈가 그대로 캐릭터의 기본 자세**가 되고 애니메이션이 그 위에 얹힌다.
- **5조각 구성**: 몸통+머리 / 좌팔 / 우팔 / 좌다리 / 우다리. 관절은 **어깨·골반만**
  (팔꿈치·무릎 없음), 머리는 몸통에 포함(골격 `bipedal5`).
- **픽셀아트 보존**: 업로드·자르기·렌더 전 구간에서 보간을 끈다(`image-rendering: pixelated`).
- **가이드 비율 조정**: 몸통 길이·너비, 어깨 높이/너비, 골반 너비, 팔·다리 길이/두께를
  슬라이더로 바꿔 캐릭터 체형(짧은 몸통·긴 다리 등)에 가이드를 맞춘다. 이 비율은 번들의
  `proportions` 로 저장되어, 관절 위치가 바뀐 채로 상대 화면·애니메이션에 동일 적용된다.
- **동작 재사용**: 새 동작을 만들지 않는다. 코어의 고정 세트(능동 4 + 자율 2)를 그대로
  재생한다. 엔진이 각 조각을 어깨·골반 트랙(`animSource`)에 리매핑해 근사 재생한다.
- **5조각 근사(중요)**: 팔꿈치·무릎이 없으므로 표현은 몸 전체의 이동·스쿼시와 어깨/골반
  회전으로 근사한다. 지금의 네 신호는 모두 이 범위 안에서 설계돼 있어 손실이 거의 없다.
- **뒷모습(선택)**: 5단계에서 같은 자세의 뒷모습 이미지를 올리면 **앞모습과 같은 자르기
  상자**로 잘라 `slotsBack` 에 담는다. 🍑 트월킹에서 등을 보일 때만 쓰이고, 없으면 앞모습
  그대로 재생된다(등록하지 않아도 깨지지 않는다). 자르기 상자는 "보는 사람 기준"이라
  좌우를 뒤집지 않는다.
- **저장 포맷**: 프리셋과 **동일**(부위 이미지 + 리그 JSON). 같은 엔진이 구분 없이 로드한다.
  이미지는 업로드 시 다운스케일(한 변 ≤512px)하고 번들 총용량 상한(≈2MB)으로 관리한다.
- **파트너 공유**: 내 캐릭터는 상대 화면에 그려지므로, 커스텀 번들을 **Firebase Storage**
  (`rooms/{code}/characters/{userId}.json`)에 올리고 RTDB `members/{userId}.characterRef`에
  참조를 기록한다. 상대 클라이언트는 characterRef를 감지하면 번들을 내려받아 캐시·렌더한다.
  (로컬 데모 모드에서는 Storage 없이 config 에 저장해 오버레이가 바로 반영한다.)

### 캐릭터의 세 종류

| 종류 | 누가 쓰나 | 저장 위치 | 상대에게 전달 |
|---|---|---|---|
| **프리셋** | 모두 | 앱에 내장 | id 만 |
| **공용(카탈로그)** | 모두 | RTDB `catalog/{id}` (관리자만 쓰기) | id 만 — 상대가 서버에서 내려받음 |
| **개인** | 만든 사람만 선택 | 내 PC `config.json` | 방 Storage 로 번들 업로드 |

- 개인 캐릭터는 **편집·삭제**할 수 있다(설정창 타일에 마우스를 올리면 ✎ 🗑 이 뜬다).
  공용·프리셋은 편집·삭제되지 않는다.
- **관리자 지정**: Firebase 콘솔 → **Realtime Database → 데이터** 탭에서 `admins` 노드를
  만들고 그 아래 `<관리자 uid>` : `true` 를 추가한다. 그 계정으로 앱을 켜면 리깅 도구
  저장 화면에 **"공용 카탈로그에 올리기"** 체크박스가 나타난다.
  (uid 는 콘솔 → **Authentication → 사용자** 탭에서 확인한다.)

### Storage 설정 (remotwerk-aa0d2)

- 버킷 `gs://remotwerk-aa0d2.firebasestorage.app` (us-central1), 설정 값은 config 의
  `storageBucket` 로 이미 연결되어 있다.
- 현재 **테스트 모드 규칙**(30일 공개 읽기/쓰기)이라 바로 업로드/다운로드가 된다.
  기간 만료 전, `rooms/{code}/characters/**` 만 허용하는 규칙으로 조여 두는 것을 권장 —
  저장소 루트의 **`storage.rules`** 파일을 콘솔(Storage → Rules)에 붙여넣으면 된다.

## 오버레이 · 멀티 모니터

오버레이 창은 **모든 디스플레이를 합친 가상 데스크톱 전체**를 덮는다(음수 좌표 포함).
덕분에 캐릭터를 드래그하거나 자율 이동으로 **모니터 경계를 넘어** 옮길 수 있다.
모니터를 추가/제거하거나 해상도를 바꾸면 오버레이가 자동으로 다시 맞춰진다.

## 범위 밖 (Non-goals)

동작 조합/수식자, 커스텀 암호, 공유 사전, 사운드, 라벨 토글, 클릭 조회, 리액션
어휘, 상대의 접속·활동 상태 표시. 리깅 도구도 자유 올가미 분할·관절 점 찍기·팔꿈치/무릎
관절·사족 골격·사용자 정의 동작·표정 교체는 다루지 않는다(大자 5조각 정합으로 대체).
